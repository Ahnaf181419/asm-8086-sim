# ASM-8086-SIM — UI/UX Audit

**Date:** 2026-10-01 · **Commit:** `d70e289` · **Method:** rendered-screenshot review of all four routes at 1440×900 and 375×667, plus scripted measurement of contrast, tab order, console output and DOM density against the production build · **Scope:** the whole app surface

> This is a **design and usability** audit. It deliberately does not re-cover the
> engine (`docs/AUDIT-2026-09-14.md`) or responsive layout
> (`docs/plans/`, all seven merged). Where those found defects, this asks a
> different question: *is the thing that works also the right thing?*

---

## Verdict

The app is **mechanically healthy and visually coherent**, and the problems that
remain are almost all about *proportion* — how much screen each thing gets, and
how much of it is worth looking at.

The CRT-terminal identity is a real design position, not a default. It is
carried consistently: four phosphor profiles, a scanline overlay with a working
off switch, panel chrome that reads as a terminal rather than as cards, and an
engine whose output genuinely looks like the hardware it emulates. That is more
of a point of view than most study tools have, and the audit does not ask it to
be toned down.

What it does find is that the aesthetic has in several places been allowed to
set *information* decisions. A memory dump that is 89% zeroes, a lesson page
that sets long-form prose in a monospace face, and a reference page that opens
on a font table instead of its own search box are all cases where the terminal
metaphor won an argument it should have lost.

Nothing here is a crash, a broken control, or an accessibility failure.

## A. Attention and proportion

The three findings that most change the experience. All are about screen real
estate going to the wrong thing.

### A1 — The memory panel is 89% nothing 🔴

**Where:** `src/components/MemoryView.tsx`, right column of `/`

Measured on a default load: **28 rows rendered, 25 of them entirely `00 00 00
00 00 00 00 00` with `........` beside them.** The actual program data — `MSG`
and `TEMP` — occupies three rows. The remaining twenty-five are a wall of
zeroes consuming roughly half the vertical space of the primary route.

This is the first thing a student sees on the busiest screen in the app, and it
carries almost no information. It is also actively misleading at a glance:
uniform rows of `00` read as "nothing is happening" even when the program has
run.

The sizing logic itself is good — `MemoryView` measures its own container with
a `ResizeObserver` and adapts 16 bytes per row down to 8 below 560px. The gap
is that it decides *how many rows fit*, never *which rows are worth showing*.

**Direction.** Default the view to the region that has content. The assembler
already knows: `program.dataImage.length` is the end of initialised data, and
`program.symbols` gives every named span. Show that range plus a margin, and
offer "jump to zeroes" rather than making it the default. The `follow SP`
button already proves the pattern — the view can anchor to something meaningful.

**Effort:** M · **Risk:** low — `MemoryView` has no callers but `SimulatorPage`.

### A2 — On a phone, more than half the screen is chrome before any content 🟠

**Where:** `src/App.tsx`, `src/pages/SimulatorPage.tsx`, 375×667

> **Corrected 2026-10-02.** The first version of this finding claimed "≈650px of
> a 667px viewport", read off a screenshot. That was wrong. The iPhone SE
> profile renders at `deviceScaleFactor: 2`, so the 750px-wide image is device
> pixels while the viewport is 375 **CSS** pixels — band heights eyeballed in
> that image are double their real value. Measured in-page instead, the figures
> below are about half what was first published, and the finding is downgraded
> from critical to high accordingly. The shape of the problem survives; its
> severity does not.

Measured in-page via `getBoundingClientRect()` against the production build:

| Band | Height |
|---|---|
| Topbar (logo, nav, theme, CRT) | **136px** |
| Toolbar (4 actions, speed, example picker) | **162px** |
| Panel chrome | ~20px |
| **Editor panel begins at** | **318px** |
| **First line of the user's program at** | **382px** |

So **382 of 667 pixels — 57% — go to chrome before a single line of code**,
leaving roughly 285px of editor. Not the catastrophe first reported, but still
a majority of a phone screen spent on frame rather than content, and an editor
barely eight lines tall.

The two bands are not equally earned. The toolbar's four actions are what the
route is *for*. The topbar's theme picker and CRT toggle are **preferences a
student sets once**, and at 44px each (correctly, for touch) they are a
meaningful share of the 136px topbar on the device with the least room.

**Direction.** Demote by frequency of use rather than by category: theme and CRT
behind one settings affordance on narrow screens, keeping the four run controls
permanently visible. Worth doing *after* the memory-panel work (A1), since that
changes what the stacked mobile layout is trying to fit.

**Effort:** M · **Risk:** medium — touches the shell every route shares.

### A3 — The Instruction Reference opens on a font table 🟠

**Where:** `src/pages/ReferencePage.tsx:59-91`

The DOM order is:

```
59  <h1>INSTRUCTION REFERENCE — 8086 subset</h1>
61  <section className="ref-font">        ← 36-row dot-matrix font table
91  <h2 className="ref-instr-h">INSTRUCTIONS</h2>
93  <input className="ref-search" …>      ← the page's primary affordance
```

A page titled *Instruction Reference* renders its instruction search **below a
36-row table about a 5×7 dot-matrix font**. At 1440×900 the search box is not
visible on load at all; on a phone it is several screens down.

The font table is good work and belongs on this page — it supports lesson 24.
It is simply in the wrong slot: it serves one lesson, while the instruction
search serves every lesson and the exam.

**Direction.** Instruction search and table first, directly under the `h1`.
Move the font table below the register table, or put it behind a `<details>` the
way the hardware route already handles its port map.

**Effort:** S · **Risk:** low — pure reordering of JSX siblings.

### A4 — Three of the four themes fail contrast on secondary text 🔴

**Where:** `src/styles/global.css` — the `--text-faint` override in each
`html[data-theme='…']` block

The green theme was contrast-tuned deliberately; `global.css` still carries the
comment recording it:

```css
/* was #4a6a4a (3.09:1) — carried memory addresses and ASCII, below AA.
   #6b8f6b measures 5.14:1 on --panel. */
--text-faint: #6b8f6b;
```

**That measurement was never repeated for the other three phosphor profiles.**
Each redefines `--text-faint` with a value chosen to look right, and three of
them land below AA:

| Theme | `.reg-signed` | `.statusbar .hint` | `.console-empty` | `.topbar .meta` |
|---|---|---|---|---|
| **Green** | 5.17 ✅ | 4.97 ✅ | 5.17 ✅ | 5.34 ✅ |
| **Amber** | **4.46** ❌ | **4.27** ❌ | **4.46** ❌ | 4.62 ✅ |
| **Cyan** | **4.42** ❌ | **4.18** ❌ | **4.42** ❌ | 4.59 ✅ |
| **Slate** | **3.92** ❌ | **3.55** ❌ | **3.92** ❌ | **4.17** ❌ |

Slate is the worst at **3.55:1**, and it is the profile most likely to be chosen
by someone who finds the phosphor themes hard to read — so the accessibility
affordance is itself the least accessible option.

The affected text is not decorative. It carries register sign values, the
keyboard-shortcut hint, and the console's empty-state instruction.

**Direction.** Re-measure `--text-faint` per theme against that theme's
`--panel` and `--panel2`, exactly as the green comment documents, and raise each
until it clears 4.5. `--text-ghost` exists precisely so genuinely decorative
text can stay dim — the failing selectors should use whichever token is correct
after measurement.

This is worth a guard rather than a one-time fix: a small test that asserts the
ratio for each theme would stop the next palette from reintroducing it. The
Playwright suite can compute it in-page, which is how these figures were
obtained.

**Effort:** S to fix, M with the guard · **Risk:** low — token values only.

## B. Typography and reading

### B1 — Long-form teaching prose is set in a monospace face 🟠

**Where:** `src/styles/global.css` — `html, body, #root { font-family: var(--mono) }`

Every word in the app is IBM Plex Mono, including the 25 lessons of explanatory
prose that are the product's actual content. On `/lessons/machine-basics` the
body copy measures roughly **95–100 characters per line** — against the
conventional 65–80 maximum, and monospace is the worst case for a long measure
because every glyph occupies the same width, removing the varied word-shapes
readers use to navigate a line.

**This is the audit's most consequential finding and also its most debatable,
so it is worth being precise about the tradeoff.** Monospace everywhere is
clearly deliberate: it is what makes the CRT identity hold together, and it is
unambiguously right for code, registers, memory dumps and port tables, where
column alignment carries meaning. The question is only whether it should also
govern three paragraphs about how a bus works.

It need not be all-or-nothing. A proportional face for `.lessons-content p`,
`li` and `td` — with mono retained for every `code`, `pre`, table of bytes and
panel — would keep the terminal identity exactly where it is doing work and
remove it where it is only costing reading speed. The lesson route is already
visually distinct from the simulator chrome, so the seam is natural.

If the decision is to keep mono everywhere, the cheap half of the fix still
applies: **cap the measure.** `.lessons-content` is `max-width: 900px`; at the
current size that is ~100 characters. Around 680px would land near 75.

**Effort:** S (measure only) / M (second face) · **Risk:** low — scoped to
`.lessons-content`.

### B2 — The lesson list is 25 flat items with no grouping 🟡

**Where:** `src/components/LessonsNav.tsx`

The sidebar lists 25 lessons as one undifferentiated column, but the content has
obvious sections: 1–14 console fundamentals, 15–20 hardware interfacing, 21–22
practice twins, 23 the lab runsheet, 24–25 assignments. Finding "the hardware
ones" currently means reading 25 titles.

**Direction.** Section headings in the sidebar. The data already supports it —
`lesson.source` distinguishes "Lecture N" from "Laboratory N" from
"Assignment" — so grouping can be derived rather than hand-maintained.

**Effort:** S · **Risk:** low.

## C. Consistency

### C1 — Three casing conventions in one toolbar 🟡

**Where:** `src/components/hardware/HardwareLab.tsx`

The Hardware Lab toolbar simultaneously uses:

- lowercase — `run`, `step`
- UPPERCASE — `RESET HW`
- Title Case — `Board`, `Split`, `Code`, `Studio`

Three conventions in one row of controls. The simulator toolbar is consistently
lowercase, so the two routes also disagree with each other.

**Direction.** Pick lowercase, matching the simulator and the terminal idiom.

**Effort:** S · **Risk:** none.

### C2 — The auto-assemble checkbox is the one unthemed control 🟡

**Where:** `src/styles/global.css:383`

```css
input[type='range'] { accent-color: var(--accent-dim); width: 110px; }
```

`accent-color` is set for range inputs and nothing else, so the auto-assemble
checkbox renders in the browser's default blue — clearly visible in the phone
screenshot as the only non-green pixel in the interface. It is a one-line fix
and it is the single most obvious break in an otherwise disciplined palette.

**Direction.** `accent-color: var(--accent-dim)` on `input[type='checkbox']`, or
on `:where(input)` generally.

**Effort:** S · **Risk:** none.

## D. Affordance and feedback

### D1 — The speed slider never says what speed is selected 🟠

**Where:** `src/pages/SimulatorPage.tsx`

The control is a bare label and a range input. The selected value — one of
1 / 10 / 60 / 400 / 3000 instructions per frame — appears only in a `title`
tooltip and in `aria-valuetext`. So it is available to a screen reader and to a
mouse user who hovers and waits, and **to nobody on a touchscreen at all.**

A student stepping through a program has a real need to know whether they are
at 1 or 3000, and the five stops are not self-evident from thumb position.

**Direction.** Render the value beside the slider. The string already exists for
the tooltip.

**Effort:** S · **Risk:** none.

### D2 — The Hardware Lab shows nine inert peripherals regardless of the program 🟠

**Where:** `src/components/hardware/HardwareLab.tsx`

The board always renders all nine devices. With the default example loaded —
*Dot Matrix: ASM-8086* — eight of the nine are dark outlines that the program
will never touch, and the one that matters has no more prominence than the rest.

The information to do better already exists and is already wired: `portMap.ts`
is the single port registry, and the bus records every cycle. The route knows
which devices a program drives as soon as it runs.

**Direction.** Keep all nine (the board metaphor is the point), but mark the
ones the loaded program actually addresses — a border, a label, or dimming the
rest. This was listed as deferred in plan 007 and remains the biggest open
opportunity on that route.

**Effort:** M · **Risk:** low.

### D3 — The thermometer starts at its minimum 🟡

**Where:** `src/engine/devices/thermometer.ts:11,13`

```ts
private celsius = -40
reset() { this.celsius = -40 }
```

The device boots at −40 °C, the bottom of its range, which `onRead` maps to byte
`0`. A student loading the *Thermometer → 7-Segment* example and pressing run
sees the display show `0` and reasonably concludes nothing happened.

Unlike the `Pressure Guage` spelling — which `titles.ts` documents as a
deliberate reproduction of the upstream kit — there is no comment suggesting
−40 is intentional fidelity. If it is, a one-line comment would stop it being
re-reported; if it is not, room temperature makes a far better first run.

**Effort:** S · **Risk:** low — but check `tests/hardware.spec.ts`, which may
pin the current value.

## E. Navigation and copy

### E1 — The toolbar's "lessons" button duplicates the nav 🟡

`SimulatorPage`'s toolbar ends with a `📖 lessons` button that navigates to the
same place as the `lessons` link three centimetres above it in the topbar. On
desktop it is redundant; on a phone it occupies one of the scarcest rows in the
app (see A2).

**Effort:** S · **Risk:** none.

### E2 — Implementation vocabulary surfaces in the UI 🟡

The hardware route's disclosure reads **"I/O PORT MAP (Constants.h Reference)"**.
`Constants.h` is a file in the original MFC emulator's source. A student reading
it has no way to know that, and no reason to care.

The design rule this breaks is naming things by what the user recognises rather
than how the system is built. "I/O port map (MDA-8086 trainer)" says the same
thing in the user's vocabulary — and the reference page already uses exactly
that phrasing for its own copy of the table.

**Effort:** S · **Risk:** none.

### E3 — Dense meta-strings carry real information past the eye 🟡

Two strings do heavy lifting in small, dim type:

- status bar: `F5 run/pause · F10 step · F4 reset · INDEC.ASM / OUTDEC.ASM auto-include`
- reference: `one byte per column · five bytes per glyph · bytes in binary — read top row first (bit 0 = top row, bit 6 = bottom) · columns go left → right to ports 2000H…2027H (see lesson 24)`

The second is a 180-character sentence set at 11px. Both mix unrelated facts
with middle dots: keyboard shortcuts sit beside an include-path behaviour that
has nothing to do with them.

**Direction.** Split by kind. Shortcuts are reference material and could live
behind a `?` affordance; the auto-include note is a property of the editor and
belongs near it. The font-table preamble wants to be two or three short lines.

**Effort:** S · **Risk:** none.

## What is already right

Stated because several of these are load-bearing and easy to regress:

- **Contrast passes throughout the default P1 Green theme** — 4.97 to 7.40
  across eight token pairs. This is the result of a deliberate earlier pass, and
  `global.css` still carries the comments explaining which values were raised
  and why (`--border-bright` for SC 1.4.11, `--text-faint` for AA). The method
  was sound; it simply was not re-run for the other three themes (A4).
- **Keyboard order is logical and trap-free**, and `:focus-visible` is styled
  globally with a comment recording that focus was once invisible everywhere.
- **Zero console errors** on any route.
- **`prefers-reduced-motion` genuinely works** — it stops the blinking cursor,
  the waiting-input chip *and* the CRT scanline overlay. The last is the one
  most projects miss.
- **The theme system is real**, not decorative: four phosphor profiles each
  redefine the full token set including editor syntax colours, and the choice
  persists through `safeStorage`.
- **Semantic markup has been maintained** — `role="log"` on console output,
  `role="img"` on every device SVG, `aria-pressed` on toggles, and flag
  explanations inlined into accessible names.
- **`MemoryView` adapts to its container** with a `ResizeObserver` rather than a
  breakpoint, dropping 16 bytes per row to 8 when narrow.

## Intermittent unit-test failure — IDENTIFIED AND FIXED 2026-10-02

**Status: resolved.** Left in full below because the hunt is the useful part.

**It was `tests/dot-matrix-rotate.spec.ts`.** Those tests drive the real 8086
interpreter — `runUntil` advances the machine in 20,000-instruction slices up to
2,500 times waiting for a display state — and take 6–8s each. Inside the full
parallel suite, under CPU contention, two of them crossed vitest's **5s default
timeout**. The file already contained the clue: its slowest test carried an
explicit `{ timeout: 30_000 }`, so someone had hit this once and fixed only the
one test that bit them.

Caught by running the full suite immediately after an unrelated CSS change: two
failures, both in that file, both ~6–8s. It never reproduced in isolation,
including under deliberate load, which is why the earlier hunt missed it — the
contention has to come from the *rest of the suite* running in parallel.

Fixed by raising the budget at the `describe` level so the whole file is covered
rather than whichever test happens to be slowest today. Not masking: every test
still asserts an exact display state. Four consecutive full-suite runs clean.

The original record follows.

**Status (as first recorded): real, unidentified, low frequency.**

While verifying the final batch, `npm test` failed once with
`1 failed | 647 passed (648)` on the second of three consecutive runs. One
executor independently reported the same symptom earlier in the session and
also could not identify the test. It has **not** reproduced since: 14 further
full-suite runs, 8 of them under deliberate CPU contention, and 10 isolated runs
of the prime suspect all passed.

The prime suspect is `tests/pages-smoke.spec.tsx`. It is the only jsdom file
that mounts CodeMirror and drives a real `requestAnimationFrame` loop, it
already carries an explicit 20s timeout for exactly this reason, and it has
grown from 2 tests to **20** across this session's work. A timing-sensitive
test under load is the shape that fits.

**Why it matters more than its frequency suggests:** CI's `build` job runs
`npm test`, and `deploy` needs `build`. A roughly 1-in-10 flake therefore blocks
a deploy on a change that is fine.

**Not mitigated deliberately.** Adding `retry` to vitest would hide it, and a
hidden flake in the one suite that gates deployment is worse than a visible one.
The honest next step is to catch it — run the suite in a loop under load with
`--reporter=verbose` until it fires, then fix the test rather than the symptom.

## Method and limits

Screenshots were taken against the **production build** served by
`npm run preview`, at 1440×900 and 375×667, using the Playwright project
configuration already in the repo. Contrast ratios were computed in-page from
resolved `getComputedStyle` values against each element's nearest painted
ancestor background, so they reflect what actually renders rather than what the
tokens declare. Tab order was walked with twelve synthetic `Tab` presses from
document start.

**A measurement lesson, recorded because it produced a wrong published number:**
screenshots from the phone project are **device** pixels at 2× scale, not CSS
pixels. Any dimension read off one must be halved before it is compared with a
CSS viewport. A2's original figures were not, and overstated the finding by
roughly 2×. Measure in-page with `getBoundingClientRect()`; use screenshots to
see *what* is wrong, never to measure *how much*.

**Not covered:** screen-reader output was not verified with an actual screen
reader (roles and names were read from the DOM); no testing on real iOS or
Android hardware, or on Safari or Firefox — all rendering evidence is Chromium;
no user testing, so every claim about comprehension is inference from structure
rather than observation. Contrast **was** measured across all four themes
(A4), but only for six secondary-text selectors on the simulator route — a full
per-theme sweep of every token pair has not been done, and Amber, Cyan and Slate
should be assumed to hold further failures until it is.
