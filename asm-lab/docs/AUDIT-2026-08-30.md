# ASM-LAB — Independent Audit & Improvement Review

**Date:** 2026-08-30
**Scope:** the whole `asm-lab/` application — engine, hook, components, pages, styling, build, tests
**Auditor:** fresh read of every source file, plus live verification (probe tests + headless-browser screenshots)
**Baseline at time of audit:** `npx tsc -b` clean · `npx oxlint` clean (0 warnings) · `npx vitest run` **72/72 passing** · `npm audit` **0 vulnerabilities**

> **Status:** the findings below were audited first, then fixed the same day. §11 records what was done, what was measured, and what is deliberately still open. The finding write-ups in §3–§7 are left as originally written, so their file/line references describe the *pre-fix* code.

> This is a *second-pass* audit. The repo already carries `asm-lab/AUDIT.md` from an earlier review, which fixed 5 criticals and 9 importants. Everything below is **new** — none of it is a re-report of an item that audit closed. Two of its claims turned out not to hold; those are called out explicitly (H3, M11).

## 0. Verdict

The engine is genuinely good. The layering (`engine/` → `useMachine` → components) is clean, the flag formulas are canonical, the jump-condition table is complete including aliases, and MUL/DIV/IDIV and INT 21H AH=0Ah semantics are faithful. 72 engine tests pass.

The **problems are concentrated in two places the test suite cannot see**:

1. **The UI has no tests at all.** There is no jsdom environment, no `@testing-library`, no `test` block in `vite.config.ts`. Every high-severity finding below except H3/H4 lives in code that no test can execute.
2. **The simulator layout is broken in a way that is invisible from the code** and only shows up when you render it — roughly 40% of the viewport is dead space, and the console panel has zero height.

Two of the four high-severity findings (H1, H2) are things a user sees within five seconds of opening the app. Neither is subtle once you look at a screenshot; neither is detectable from reading a diff.

**Headline:** the *step-debugger highlight — the single most important feature of the tool — points at the wrong line on every program.**

## 3. High-severity findings in detail

### H1 — The current-line highlight decorates the wrong line, on every program

**Files:** `src/components/editorLineField.ts:17`, `src/pages/SimulatorPage.tsx:86-97`

```ts
// editorLineField.ts:15-18
function lineDeco(line: number | null): RangeSet<Decoration> {
  if (line == null) return Decoration.none
  return Decoration.set([Decoration.line({ class: 'editor-current-line' }).range(line)])
}
```

`Decoration.line(...).range(pos)` takes a **document character offset** — CodeMirror's own doc string for it reads *"add DOM attributes to the line starting at the given position."* The caller passes a **0-based line index**:

```ts
// SimulatorPage.tsx:90-96
let line = stmt && (...) ? stmt.pos.line - 1 : null
if (line != null) {
  const maxLine = view.state.doc.lines - 1
  if (line > maxLine) line = maxLine       // ← clamps an index, then uses it as an offset
  ...
}
view.dispatch({ effects: setCurrentLineEffect.of(line) })
```

Measured against a real 12-line program:

```
stmt on source line  7: code passes offset 6 -> highlights line 1 (should pass offset 60)
stmt on source line  9: code passes offset 8 -> highlights line 1 (should pass offset 93)
stmt on source line 10: code passes offset 9 -> highlights line 1 (should pass offset 107)
```

The 1440×900 screenshot confirms it live: the status bar reads `IP=0100 · editor.asm:16 · MOV` while the editor highlights **line 1**.

Because offsets are far smaller than the document length, this never throws — it silently lands on whichever line contains that character offset, which for any realistic source is line 1 or 2. The clamp added by the previous audit (U2) stopped the `RangeError` but cemented the wrong unit, so the bug now reads as intentional.

**Fix**

```ts
// editorLineField.ts — take an offset, and say so
function lineDeco(pos: number | null) {
  if (pos == null) return Decoration.none
  return Decoration.set([Decoration.line({ class: 'editor-current-line' }).range(pos)])
}

// SimulatorPage.tsx — convert line number → offset, clamped in line-number space
const doc = view.state.doc
const n = stmt && (stmt.pos.file === 'editor.asm' || stmt.pos.file === '') ? stmt.pos.line : null
const pos = n == null ? null : doc.line(Math.min(Math.max(n, 1), doc.lines)).from
view.dispatch({ effects: setCurrentLineEffect.of(pos) })
```

Rename the effect to `setCurrentLineOffsetEffect` so the unit is in the name — this is exactly the kind of mistake a bare `number` invites.

### H2 — The simulator throws away ~40% of the viewport; the console panel has no height

**Files:** `src/styles/global.css:106, 146, 149-160`, `src/pages/SimulatorPage.tsx:151`

Three independent defects compound:

**(a) A phantom second grid row.**

```css
.sim-layout {
  display: grid;
  grid-template-columns: minmax(340px, 1fr) minmax(300px, 420px);
  grid-template-rows: minmax(0, 1.4fr) minmax(140px, 1fr);   /* two rows… */
  height: 100%;
  overflow: hidden;
}
.sim-br { grid-column: 2; }                                   /* …targets a non-grid-item */
```

`.sim-layout` has exactly **two** children — `.sim-left` and `.sim-right` — which auto-place into row 1, columns 1 and 2. Row 2 is empty and still claims `1fr`. At 900px tall that is **~355px of blank screen** below the app.

`.sim-br` is applied to the MEMORY panel, which is a child of `.sim-right`, *not* a grid item of `.sim-layout` — `grid-column` on it is inert. Both facts point the same way: this rule set is a leftover from an earlier 2×2 panel grid that was refactored into two column wrappers, and the row template was never updated.

**(b) `.editor-panel` has no CSS rule at all.** `SimulatorPage.tsx:151` sets `className="editor-panel"`; `global.css` never defines it. So the SOURCE panel is `flex: 0 1 auto` inside `.sim-left` and sizes to its content instead of filling the column.

**(c) The console body collapses to zero.** `Console.tsx:44` sets `height: 100%` on its root, but its parent `.term-body` is `display: block` with auto height, so `100%` resolves to auto → 0. In the screenshot the OUTPUT panel is a bare title bar with nothing under it. The same reason makes `.editor-wrap { flex: 1 }` (`global.css:276`) inert — `.term-body` is not a flex container.

**(d) The narrow breakpoint clips instead of scrolling.** At 900×700 the editor is cut mid-line, the OUTPUT title overlaps the status bar, and the register grid is sheared through the `BP` row. `@media (max-width: 1000px)` sets `.sim-layout { height: auto; overflow-y: auto }` but its parent `.page` (line 106) keeps `overflow: hidden`, and `.sim-left { min-height: 320px }` sets a *floor* rather than letting content size the column — so the four stacked panels are squeezed into 320px and clipped.

**Fix** — see §4, which rebuilds the layout as one coherent system rather than patching four rules.

### H3 — Binary literals parse as decimal; garbage numbers are accepted silently

**File:** `src/engine/parser.ts:221-231`

```ts
export function parseNumber(text: string): number {
  const m = /^([0-9][0-9A-Fa-f]*)([HhBbDd]?)$/.exec(t)
  ...
  if (suffix === 'b') return parseInt(digits, 2)
```

`B` and `D` are themselves hex digits, and the first group is greedy, so the optional suffix is **never reached** for a `B`/`D`-suffixed literal:

```
'101B'  -> groups ["101B", ""]  => 101     (should be 5)
'1010B' -> groups ["1010B",""]  => 1010    (should be 10)
'10D'   -> groups ["10D",  ""]  => 10      (right, by accident)
'1D2'   -> groups ["1D2",  ""]  => 1       (should be an error)
'0AH'   -> groups ["0A",  "H"]  => 10      (right — H is not a hex digit)
```

Verified end-to-end: `MOV AX, 101B` leaves `AX = 0x0065` (101). `X DB 1010B` is rejected with the *misleading* message `value 1010 out of range for byte (DB)` — a student reading that has no way to work out what actually went wrong.

`PLAN.md` §4.3 lists binary `…B` as a supported immediate format, so this is a spec violation, not an out-of-scope idiom. It also contradicts `AUDIT.md` M8, which records `1D2` as "handled as error" — it is not; it silently evaluates to 1.

**Fix**

```ts
export function parseNumber(text: string): number {
  const t = text.trim()
  let m: RegExpExecArray | null
  if ((m = /^([0-9][0-9A-Fa-f]*)[Hh]$/.exec(t))) return parseInt(m[1], 16)
  if ((m = /^([01]+)[Bb]$/.exec(t)))            return parseInt(m[1], 2)
  if ((m = /^([0-9]+)[Dd]?$/.exec(t)))          return parseInt(m[1], 10)
  return NaN   // '1D2', '0FF' (no suffix), '12G' → caller reports "bad number"
}
```

Test matrix to add: `101B→5`, `1010B→10`, `11B→3`, `0AH→10`, `0FFH→255`, `12H→18`, `10D→10`, `255→255`, and `1D2`/`0FF`/`2B` → assembly error with a message naming the token.

### H4 — Unsigned `DIV` builds a negative dividend when `DX ≥ 8000h`

**File:** `src/engine/cpu.ts:290`

```ts
const dividend = (this.getReg('DX') << 16) | this.getReg('AX')
```

JavaScript bitwise operators coerce to **signed** 32-bit. `0xFFFF << 16` is `-65536`, not `4294901760`. So for any `DX` with bit 15 set, `DIV` divides a negative number, the quotient is wrong, and the `q > 0xffff` divide-overflow guard never fires.

Verified:

| Setup | Real 8086 | ASM-LAB |
|---|---|---|
| `DX=FFFFh AX=FFFFh DIV BX(=FFFFh)` | divide overflow (`INT 0`) | runs on, wrong quotient, no error |
| `DX=8000h AX=0000h DIV BX(=2)` | divide overflow (0x40000000 > 0xFFFF) | returns `AX=0 DX=0`, no error |

`IDIV` is **correct** and must not be changed: its `toS32(dividend)` is a no-op on an already-signed value, which is precisely the semantics signed division wants.

**Fix**

```ts
// DIV: unsigned 32-bit dividend — arithmetic, not bitwise
const uDividend = this.getReg('DX') * 0x10000 + this.getReg('AX')
// IDIV: keep the signed reading
const sDividend = toS32((this.getReg('DX') << 16) | this.getReg('AX'))
```

Both stay exactly representable as JS doubles (max `2³²−1`), so no precision concern.

## 4. UI, layout, positioning & flexibility

This is what the user asked about most directly, so it gets its own treatment. The visual language — phosphor-green CRT, panel chrome, scanlines — is *good* and worth keeping. The problems are structural, not aesthetic.

### 4.1 What the screenshots show

| Viewport | Observed |
|---|---|
| 1440×900 | App occupies the top ~545px. Bottom **355px is blank**. OUTPUT panel = title bar only, no body. Editor sized to its 16 lines instead of filling. Current-line highlight on line 1 while the status bar says line 16. |
| 900×700 | Editor clipped mid-line 7. OUTPUT title sheared by the status bar. Register grid cut through the `BP` row. Nothing scrolls — it just clips. |
| `/lessons` 1440 | Clean and readable. ~330px of unused gutter right of the 900px content column. |
| `/reference` 1440 | Clean. Description column absorbs all slack while Syntax stays cramped. |

### 4.2 Root cause

The simulator layout mixes three positioning strategies that don't agree with each other:

- a **grid** whose row template describes a layout that no longer exists,
- **flex columns** whose children never declare a vertical budget (`flex: 0 1 auto` everywhere),
- **inline styles** for spacing and sizing scattered across ~12 sites in `SimulatorPage.tsx` and `MemoryView.tsx`, outside the design system that `PLAN.md` §2 defines.

Nothing owns the vertical axis, so every panel sizes to content and the leftover space is simply abandoned.

### 4.3 Proposed layout system

**Step 1 — one row, columns own their internals.**

```css
.sim-layout {
  display: grid;
  grid-template-columns: minmax(420px, 1fr) minmax(320px, 440px);
  grid-template-rows: 100%;          /* was: two rows, one of them empty */
  gap: 10px;
  padding: 10px;
  height: 100%;
  min-height: 0;
  overflow: hidden;
}
/* delete .sim-br entirely — it targets a non-grid-item */
```

**Step 2 — give every panel an explicit vertical budget.**

```css
.sim-left, .sim-right {
  display: flex; flex-direction: column; gap: 10px; min-height: 0;
}
.toolbar        { flex: 0 0 auto; }
.editor-panel   { flex: 1 1 62%; min-height: 220px; }
.console-panel  { flex: 1 1 38%; min-height: 130px; }
.sim-left > .statusbar { flex: 0 0 auto; }
.regs-panel     { flex: 0 0 auto; }
.mem-panel      { flex: 1 1 auto; min-height: 180px; }
```

Add `className="console-panel"`, `"regs-panel"`, `"mem-panel"` in `SimulatorPage.tsx` (`.editor-panel` is already passed and just needs a rule).

**Step 3 — let fill-panels actually fill.** `.term-body` must be a flex container for its `flex: 1` children to mean anything. Scope it so table panels are unaffected:

```css
.editor-panel > .term-body,
.console-panel > .term-body {
  display: flex;
  flex-direction: column;
  padding: 0;              /* the editor supplies its own gutter padding */
}
.console-panel > .term-body { padding: 8px 10px; }
```

**Step 4 — make the narrow breakpoint scroll instead of clip.**

```css
@media (max-width: 1100px) {
  .page        { overflow: auto; }        /* ← the missing piece; was hidden */
  .sim-layout  { grid-template-columns: 1fr; grid-template-rows: auto;
                 height: auto; overflow: visible; }
  .sim-left, .sim-right { min-height: 0; }   /* was 320px — a floor that caused the clipping */
  .editor-panel  { flex: 0 0 clamp(240px, 45vh, 520px); }
  .console-panel { flex: 0 0 clamp(130px, 22vh, 280px); }
  .mem-panel     { flex: 0 0 auto; }
}
@media (max-width: 640px) {
  .topbar     { flex-wrap: wrap; gap: 8px 12px; }
  .topbar .meta { display: none; }
  .ref-search { width: 100%; }             /* fixed 320px overflows small screens today */
  .lessons-content { padding: 16px 18px 60px; }
}
```

**Step 5 — real flexibility: a draggable split.** The highest-value ergonomic upgrade is letting the user rebalance editor vs. console, and left column vs. inspector. Two options:

- *Cheap (≈20 lines):* `resize: vertical; overflow: auto` on `.editor-panel`, plus a `--sim-split` CSS custom property on `.sim-layout` driven by a thin drag handle, persisted to `localStorage`.
- *Proper (≈80 lines):* a small `<Splitter>` component wrapping the two panes with pointer-event dragging, keyboard support (`ArrowLeft/Right` on a `role="separator"`), and a double-click reset.

Either restores what a fixed `minmax(300px, 420px)` inspector column takes away: a student debugging a long array program wants a tall memory view; a student writing code wants a tall editor.

**Step 6 — make the memory view size itself.** `MemoryView.tsx:11-12` hard-codes `ROWS = 12` and `BYTES_PER_ROW = 8`. With Step 2 the panel has a real height, so derive both:

```ts
// rows from measured height, bytes-per-row from measured width
const ref = useRef<HTMLDivElement>(null)
const [box, setBox] = useState({ w: 0, h: 0 })
useLayoutEffect(() => {
  const el = ref.current; if (!el) return
  const ro = new ResizeObserver(([e]) =>
    setBox({ w: e.contentRect.width, h: e.contentRect.height }))
  ro.observe(el); return () => ro.disconnect()
}, [])
const perRow = box.w >= 560 ? 16 : 8
const rows   = Math.max(4, Math.floor(box.h / ROW_PX))
```

Also fix `symbolAt` (`MemoryView.tsx:65, 83`): it only tests a **row's start address**, so a symbol beginning mid-row is never labelled. Test every byte in the row and label with the first match.

## 5. Accessibility

The theme is mostly well-chosen — `--text`, `--accent`, `--warn`, `--info`, `--err` all clear WCAG AA comfortably. Two tokens don't, and there is no keyboard story at all.

| Token | On | Ratio | Verdict |
|---|---|---|---|
| `--text` `#c8f5c8` | `--bg` | 16.06 | ✅ AA |
| `--accent` `#33ff66` | `--bg` | 14.48 | ✅ AA |
| `--warn` `#ffcc44` | `--panel` | 12.52 | ✅ AA |
| `--info` `#66ccff` | `--panel` | 10.43 | ✅ AA |
| `--text-dim` `#7fae7f` | `--panel` | 7.40 | ✅ AA |
| **`--text-faint` `#4a6a4a`** | `--panel` | **3.09** | ❌ fails AA (needs 4.5) |
| **`--border-bright` `#2f4f2f`** | `--panel` | **2.04** | ❌ fails SC 1.4.11 (needs 3.0) |

**M4.** `--text-faint` is not decoration — it carries **memory addresses** (`.mem-addr`), the ASCII column, `.reg-signed` values, the symbol legend, and the keyboard-shortcut hints. And `body::after` (`global.css:37-51`) multiplies 12% black over one row in every three, pushing the effective ratio lower still. Raise it to about `#6b8f6b` (≈5.1:1) and let `--text-ghost` take over for genuinely decorative text.
`--border-bright` is the default border on every `button` and `select`; raise to ≈`#3f6b3f` for a 3:1 control boundary.

**M5.** `global.css` styles `:hover` on every interactive element and `:focus-visible` on none; `.cm-editor.cm-focused { outline: none }` (line 272) strips the editor's. Add:

```css
:where(button, a, select, input, [tabindex]):focus-visible {
  outline: 2px solid var(--accent);
  outline-offset: 2px;
}
.cm-editor.cm-focused { outline: 1px solid var(--accent-dim); }
```

**M6.** Icon-only controls have no accessible name: `▲`/`▼` (`MemoryView.tsx:98-99`), `⇥ step`, `⟲ reset`, `❚❚ pause`. `title` is not a reliable accessible name — add `aria-label`. The speed slider (`SimulatorPage.tsx:129`) needs `aria-valuetext={`${SPEEDS[speedIndex]} instructions per frame`}`, since its raw value is an array index. The memory `data`/`stack` toggle should be `role="tablist"` with `aria-pressed`, and the run button's label change (`run`↔`pause`) should be announced via `aria-live="polite"` on the status chip.

**L11.** No `prefers-reduced-motion` guard. The logo cursor (`global.css:82`) and the waiting-input chip (line 224) blink indefinitely:

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation: none !important; transition: none !important; }
  body::after { display: none; }   /* the scanline overlay too */
}
```

**L12.** `html { font-size: 14px }` (line 28) is a fixed pixel root, which defeats browser font-size preferences. Move to `font-size: 100%` with a `--fs-base: 0.875rem` token and express sizes in `rem`.

**Worth adding:** a scanline/glow toggle. The CRT effect is the identity of the design, but 12% multiply over all text is a real legibility cost during long study sessions. A `--crt: 0|1` switch persisted to `localStorage` keeps the aesthetic as the default without trapping anyone in it.

## 6. Engine — remaining medium findings

**M1 — `HLT` assembles then dies at runtime.** `assembler.ts:431` lists `HLT` among the zero-operand mnemonics, so it passes validation; `cpu.ts`'s `exec` switch has no `HLT` case, so it reaches `default:` and throws `instruction 'HLT' not implemented` (verified). Add `case 'HLT': this.status = 'halted'; return`. Then add a **guard test** that asserts every mnemonic `operandCount()` accepts is reachable in `exec` — this class of drift will recur otherwise.

**M2 — source without `.CODE` silently assembles to nothing.** `assembler.ts:112` skips any statement whose `segment !== 'code'`, and segments start as `'none'`. Verified: `assemble('MOV AX, 5\nMOV BX, 7\n')` returns `program != null`, `errors: []`, `byAddr.size === 0`. The UI then shows `READY`, `run` does nothing, and nothing explains why. Emit an error when instruction statements were parsed but `firstInstr === null`: *"no instructions in a code segment — add a `.CODE` directive before your instructions"*. This is the most likely first-five-minutes failure for a student pasting a snippet from a lecture slide.

**M8 — `DUP` count must be a numeric literal.** `parser.ts:168-172` requires `g[0].kind === 'number'`, so the standard MASM idiom is rejected:

```asm
N   EQU 5
ARR DB  N DUP(0)     ; → "invalid data expression"  (verified)
```

Nothing in `Resources/` currently breaks (the course files use literal counts — `ARR DW 100 DUP (?)`), but lessons teach `EQU` and `DUP` in the same unit, so a student following them will hit this. Requires deferring the DUP count to expression-evaluation time; the two-phase data layout added by the previous audit already provides the right seam, but sizes must then be computed after EQU resolution. Effort **M**, not S.

**M10 — `RET AX` assembles.** `checkSizes` (`assembler.ts:687`) returns without validating RET's operand; `cpu.ts:368` then reads `ops[0].k === 'imm' ? … : 0`, so a register operand becomes a silent plain `RET`. Reject non-immediate RET operands at assembly time.

**Also worth a defensive pass** (low severity, listed for completeness):

- `cpu.ts:203-204` — `INC`/`DEC` unconditionally add `cf` to `lastChanges`, so CF flashes on every increment even though it never changed.
- `cpu.ts:510-513` — `setReg` on a segment register never records a change; `MOV DS, AX` never flashes.
- `cpu.ts:187-191` — `setArithFlags` receives `b + carry` rather than `b`, so `ADC`/`SBB` compute OF and AF from a value that can exceed the operand width. No course program is known to hit it; worth a comment or a corrected signature rather than a rewrite.
- `cpu.ts:325` — shift counts are masked to 5 bits (80186+ behaviour); the 8086 does not mask. Fine for the course, worth a code comment.
- `assembler.ts:344` — a `NaN` DUP count propagates to `NaN` offsets and produces a zero-length data image rather than an error.

## 7. Architecture, testing & tooling

**M3 is the structural finding — the one that explains why H1 and H2 survived a previous audit.**

- `vite.config.ts` has **no `test` block**: no `environment: 'jsdom'`, no setup file. There is no way to render a component in a test.
- `tsconfig.app.json` sets `"include": ["src"]` and `tsconfig.node.json` `["vite.config.ts"]` — **`tests/` is in neither**, so `npm run build` (`tsc -b && vite build`) never typechecks the test suite. A test can drift out of sync with the engine's types and CI would stay green.

Recommended sequence:

1. Add `tests/tsconfig.json` (or extend the app config's `include` to `["src", "tests"]`) so the suite is typechecked by `npm run build`.
2. Add `jsdom` + `@testing-library/react` and a `test: { environment: 'jsdom' }` block. Note `@vitejs/plugin-react@6` + `vitest@4` need no extra wiring.
3. Write the three tests that would have caught the high-severity findings:
   - `editorLineField`: given a known doc, assert the decoration lands on the expected line — this pins H1 permanently.
   - `useMachine`: assemble → step → assert the published snapshot and `changes` sets.
   - `Console`: assert the input row is present, that a bare Enter submits, and that `onInput` receives the expected string.
4. Add the `operandCount` ↔ `exec` reachability guard from M1 — a pure-TS test, no DOM needed, that would have caught `HLT`.
5. Add the `parseNumber` table from H3.

**Other tooling notes:**

- **L17 — the project is not under version control.** `git rev-parse` fails; there is no `.git` anywhere in the tree, despite `asm-lab/.gitignore` being present and correct. That is ~4,700 lines of hand-written engine, lessons and course content with **no history and no undo**. This should be fixed before any of the changes above: `git init && git add -A && git commit`. It is the single cheapest risk reduction available here.
- **L9 — one 788 KB JS chunk** (`dist/assets/index-DtQtXib3.js`). `PLAN.md` §10 planned `React.lazy` for CodeMirror and it was never done. `React.lazy(() => import('./components/CodeEditor'))` with a `<Suspense>` skeleton moves roughly half of that off the initial load, and the Lessons/Reference routes don't need the editor at all.
- **L10** — `index.html` loads IBM Plex Mono from Google Fonts. For an offline-capable personal study aid, self-host the two weights (`woff2`, ~35 KB) so the app doesn't degrade without a network.
- **L16** — TypeScript strictness is currently inherited from TS 6's new default, not declared. `tsc --showConfig` reports `strict: undefined`, yet `noImplicitAny` and `strictNullChecks` both fire (verified). Add `"strict": true` explicitly to `tsconfig.app.json` so it survives a toolchain change.
- **L8** — `src/data/reference.ts` omits engine-supported `RCL RCR STC CLC CMC STD CLD XLAT JNC HLT`. Reference/engine drift; a generated-from-source table, or a test asserting the two sets match, prevents recurrence.
- Dependencies are healthy: **0 vulnerabilities**; only `typescript` (6→7) and `@types/node` (24→26) have major updates outstanding. Neither is urgent.
- `.oxlintrc.json` does not enable `typeAware` rules. Enabling `oxlint-tsgolint` would have flagged several of the dead-code items in §5 automatically.

## 8. Direction — worth considering, not defects

1. **Breakpoints and run-to-cursor.** The pseudo-address model (`PLAN.md` §4.1) was chosen precisely to make this trivial: a `Set<number>` of addresses checked in the run loop, toggled from a gutter click. This is the highest-value missing debugger feature and probably a day's work.
2. **Step-backwards.** The whole machine is 64 KB plus ~12 numbers. Snapshotting every step (or every Nth, with replay between) makes reverse-stepping cheap, and "undo the instruction I just ran" is enormously useful for someone learning flag semantics. Memory cost is the honest trade-off — cap the ring buffer.
3. **Quiz / exam-prep mode.** `PLAN.md` §6 lesson 10 already points at `Sample Online Questions.pdf` and `Mid_Semester_Question_Quanta.txt`, and `PLAN.md` §1 lists "no quiz module in v1" as a deliberate deferral. A "predict the register values, then run to check" drill would reuse the engine as-is.
4. **A "why did this flag change?" panel.** The flag formulas in `setArithFlags` are the part of the course students most reliably get wrong, and the engine already knows `a`, `b`, `r` and the operation. Showing the derivation for the last instruction turns a correct simulator into a teaching tool. Small, and unusually well-matched to what this project is for.

## 12. H5 — the editor rendered with CodeMirror's default light theme

**Missed by this audit; reported by the user as "light green texts are not visible properly" in editor.asm.**

**File:** `src/components/CodeEditor.tsx` (no theme configured), `src/styles/global.css` (the `.cm-*` overrides)

The app never gave CodeMirror a theme, so it used its built-in **light** one. Measured on the live page:

```
.cm-editor  backgroundColor = rgb(255, 255, 255)      ← pure white, inside a dark app
.cm-content color           = rgb(200, 245, 200)      ← inherited --text, a pale green
```

`#c8f5c8` on `#ffffff` is **1.21:1**. Anything the MASM stream parser did not tokenize — which is most identifiers, plus `DB`/`DW` — rendered as pale green on white and was effectively invisible. The tokens that *were* styled came from CodeMirror's light defaults (`#994400` comments, `#770088` keywords, `#aa1111` strings): readable, but completely off-palette for a phosphor-green terminal.

**Why the audit missed it.** Two failures worth naming:

1. I read `global.css` and saw `.cm-gutters`, `.cm-activeLine` and `.cm-activeLineGutter` overridden to dark with `!important`. That looked like the editor was themed. It wasn't — those rules dress the *gutter and line backgrounds* from outside, and never touch `.cm-editor`'s own background or the syntax colours. The `!important` on all three is in hindsight the tell: they were fighting a theme rather than replacing it.
2. **The evidence was in my own screenshots.** The 1440×900 capture in §3 shows a white editor pane. I was reading those images for layout geometry and did not register the colour. A screenshot only answers the question you bring to it.

**Fix.** A real CodeMirror theme (`src/components/editorTheme.ts`): `EditorView.theme(..., { dark: true })` for the chrome, plus a `HighlightStyle` mapping the stream parser's tags to the app palette. Colours are CSS custom properties in `global.css` (`--editor-bg`, `--syn-*`) so the editor tracks the rest of the design system, and the external `!important` overrides are deleted.

| Token | Colour | Contrast on `--editor-bg` |
|---|---|---|
| default text | `#c8f5c8` | 16.37 |
| label | `#b6ffcf` | 17.16 |
| symbol | `#d7f7d7` | 17.15 |
| keyword | `#4dff7d` | 15.02 |
| number | `#ffcc44` | 13.18 |
| register | `#7bd4ff` | 11.98 |
| operator | `#9ec49e` | 10.23 |
| string | `#ffa06a` | 9.90 |
| comment | `#6f9a78` | 6.20 |

Worst case **6.20:1**, up from 1.21:1. `tests/editor-theme.spec.ts` parses the tokens straight out of `global.css` and fails if any drops below 4.5:1 or if two collapse to the same value.

### Two further defects surfaced while fixing it

- **`DB` and `DW` were never highlighted.** The editor kept its own hand-written mnemonic list, and the two most common directives in the entire course were absent from it — along with `OFFSET`, `SHORT` and `HLT`. The vocabulary moved to `src/components/masmTokens.ts` (no CodeMirror imports, so tests can read it), and a drift guard asserts every mnemonic in `SUPPORTED_MNEMONICS` is highlighted. Same guard pattern as L8, third time it has caught something.

- **A regression from my own L9 code-splitting work.** Moving the highlight into `CodeEditor` stored the view in a `useRef`. On the first render the view does not exist yet, so the effect returned early — and since `currentLine` had not changed, it never re-ran. The result: **no IP marker at all until you pressed step.** My earlier end-to-end check stepped six times before looking, so it passed and hid the bug. Changed to `useState`, which re-runs the effect when the editor is created; verified on a cold load that line 16 carries the marker. The lesson is narrow and worth keeping: *verifying a fix by exercising the thing that changes it can mask a broken initial state.*
